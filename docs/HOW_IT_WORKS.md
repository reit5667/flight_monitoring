# Как работает Flight Monitor

## Суть проекта

Есть конкретная задача: найти наиболее выгодный способ добраться из точки A в точку B. Авиаагрегаторы показывают цены в моменте, но не отвечают на вопрос «а когда лучше купить?» и не следят за изменениями.

Эта система делает именно это: задаёшь маршруты, которые тебя интересуют, система регулярно собирает цены с источников, отслеживает динамику и присылает уведомление в Telegram когда появляется выгодное предложение.

При этом система устроена как настоящая Data Platform — с историей изменений, аналитикой и стандартными DE-паттернами.

---

## Слои данных

В Data Engineering принято разделять данные на слои:

| Слой | Что это | Где лежит |
|---|---|---|
| **Raw** | Исходный JSON с сайта, без изменений | `raw_storage/` (файлы на диске) |
| **Silver** | Нормализованные `Flight` объекты | Память (Python объекты) |
| **Gold** | Агрегаты: мин цена, история, лучшие предложения | PostgreSQL views / Grafana |

Bronze-слой пропущен: парсер сразу даёт нам Silver, промежуточный слой не нужен.

## Конвейер шаг за шагом

Представь конвейер: данные входят с одного конца, обрабатываются по шагам, и на выходе ты получаешь уведомление или график.

### Шаг 1 — Планировщик (Prefect)

Каждые N минут автоматически запускается задача. Она спрашивает базу данных: «какие маршруты нужно проверить прямо сейчас?» Маршруты с высоким приоритетом проверяются чаще.

Prefect — это как cron, только с UI, логами и возможностью запустить задачу вручную одной кнопкой.

### Шаг 2 — Коннекторы (Aviasales, Trip.com)

Для каждого маршрута система идёт на сайты и получает актуальные цены. Важный момент: **мы не парсим HTML** (это ненадёжно, сайты меняют вёрстку). Вместо этого используем Playwright, чтобы открыть браузер, дождаться пока сайт загрузит данные, и перехватить XHR-запрос — тот самый JSON, который сайт получает от своего собственного сервера.

Это надёжнее: структура JSON меняется реже, чем HTML.

Каждый коннектор — отдельный файл, все работают по одному интерфейсу (`BaseConnector`). Хочешь добавить новый источник — создаёшь ещё один файл, не трогая остальные.

### Шаг 3 — Raw Storage

**Сразу после получения** JSON сохраняется как файл на диск (`raw_storage/aviasales/1/2024-01-15T10:00:00.json`). Зачем? Если завтра выяснится, что парсер работал с багом — можно перепарсить старые данные без повторного запроса к сайту. Это важный принцип: **сырые данные неизменны**.

В базу данных в таблицу `raw_snapshots` записывается только метаинформация: где лежит файл, сколько рейсов нашли, когда сохранили. Нужно для аудита и для перепарсинга — берёшь `file_path` и перечитываешь с новым парсером.

### Шаг 4 — Парсеры

Сырой JSON у каждого сайта свой, разный. Парсер превращает его в единую модель `Flight` — набор полей, одинаковый для всех источников:

```
Aviasales JSON → parser/aviasales.py → Flight(provider="aviasales", price=120, ...)
Trip.com JSON  → parser/trip.py      → Flight(provider="trip", price=115, ...)
```

После парсера данные уже сравнимы между собой.

### Шаг 5 — CDC Engine

CDC расшифровывается как Change Data Capture — захват изменений данных.

Обычно CDC — это когда база данных сама отдаёт поток изменений. Но у нас внешние сайты, они ничего не отдают. Поэтому мы строим CDC сами: сравниваем два последовательных списка рейсов и находим разницу.

```
10:00 → [AirAsia: 120 USD, Malaysia Airlines: 150 USD]
11:00 → [AirAsia: 105 USD, Batik Air: 90 USD]

CDC находит:
  UPDATE: AirAsia: 120 → 105  (цена упала)
  INSERT: Batik Air: 90        (новый рейс появился)
  DELETE: Malaysia Airlines    (рейс исчез)
```

**CDC Engine — чистая функция**: принимает два списка, возвращает список событий. Не обращается к базе данных. Это важно для тестируемости — логику можно проверить без поднятия PostgreSQL.

### Шаг 6 — Уведомления (до записи в Warehouse)

Это нетривиальный момент в архитектуре: **уведомления проверяются ДО того, как CDC применяется к warehouse**.

Почему это важно? Правила сравнивают новую цену с историческим базелайном из `flights_history`. Если сначала записать изменения, а потом проверить правила — базелайн уже обновится, и правило никогда не сработает корректно. Поэтому порядок такой: CDC события → проверка правил → запись в warehouse.

**Два правила, один приоритет (первое важнее):**

1. **HISTORICAL_MIN** — новая цена ниже исторического минимума за всё время (`MIN(price)` по `flights_history`). Самый важный триггер.
2. **SIGNIFICANT_DROP** — цена упала на ≥15% ниже скользящего среднего за последние 30 дней. Порог настраивается через `PRICE_DROP_THRESHOLD_PCT`.

На одно событие срабатывает максимум одно правило — первое подходящее.

**Дедупликация:** чтобы уведомление не приходило каждый час пока цена стоит на минимуме, работает дедуп-окно: повторное уведомление по тому же рейсу и правилу не придёт раньше чем через 4 часа (`DEDUP_WINDOW_HOURS=4`). Состояние хранится в памяти процесса — при рестарте Prefect-воркера сбрасывается, уведомление может прийти повторно.

### Шаг 7 — Warehouse (PostgreSQL)

После проверки правил CDC события применяются к трём таблицам:

**`flights_current`** — актуальное состояние прямо сейчас. Одна запись на рейс, всегда обновлённая. При изменении цены делается UPDATE этой строки.

Нюанс: у чартерных рейсов нет номера (`flight_number = NULL`). Чтобы два NULL в уникальном ключе считались одним и тем же рейсом (а не разными), используется `UNIQUE NULLS NOT DISTINCT` — это фича PostgreSQL 15+.

**`flights_history`** — полная история. Никогда ничего не удаляется. Если цена изменилась 5 раз — в таблице 5 записей, у каждой есть дата начала действия и дата окончания. Это называется **SCD Type 2** (Slowly Changing Dimension) — стандартный паттерн в DE.

```
valid_from            valid_to              price   is_current
2024-01-15 10:00 UTC  2024-01-15 11:00 UTC  120     false
2024-01-15 11:00 UTC  null                  105     true
```

**`cdc_events`** — лог всех событий с подробностями: что изменилось, `old_price`, `new_price`, `changed_fields` (JSONB). Таблица растёт только вперёд — никаких UPDATE или DELETE.

### Шаг 8 — Grafana + Prometheus

**Grafana** подключена напрямую к PostgreSQL и строит графики по SQL-запросам. Никакого дополнительного API не нужно.

Дашборды:
- История цены по маршруту (из `flights_history`)
- Минимум и среднее за период
- Лучшие текущие предложения (из `flights_current`)
- Активность CDC за сутки (сколько INSERT/UPDATE/DELETE)

**Prometheus** собирает runtime-метрики воркера:
- `connector_requests_total` — кол-во запросов к источникам (success / error)
- `cdc_events_total` — счётчик CDC событий по типу
- `connector_flights_found` — сколько рейсов нашли в последнем запуске
- `pipeline_duration_seconds` — гистограмма длительности пайплайна по маршруту

Grafana читает их через datasource Prometheus и строит operational-дашборд.

## Маршруты и source_route_mappings

Маршруты — это конфигурация. Добавляешь запись в таблицу `routes`:

```
origin: HAN  (Ханой)
destination: KUL  (Куала-Лумпур)
date_from: 2026-08-03
date_to: 2026-08-17
max_price: 200       ← резерв (пока не используется в правилах)
priority: 100        ← чем выше, тем чаще проверяем
search_interval: 60  ← раз в час
enabled: true
```

Проблема: Aviasales использует код `HAN` для Ханоя, а Trip.com — тоже `HAN`, но так бывает не всегда (для Москвы это `MOW` vs `SVO`). Таблица `source_route_mappings` хранит маппинг: один маршрут в системе → разные коды для каждого источника. Это позволяет не дублировать маршруты.

```
route_id  source      source_origin  source_destination
1         aviasales   HAN            KUL
1         trip        HAN            KUL
```

## Почему именно такая архитектура

**Почему Raw Storage?** Структура XHR API сайтов меняется. Если сохранять сырые данные, то при смене формата нужно только поправить парсер и перепрогнать старые файлы — данные не теряются.

**Почему source_route_mappings?** Разные источники используют разные коды для одних и тех же аэропортов. Таблица маппингов решает это без дублирования маршрутов.

**Почему Prefect, а не cron?** Prefect даёт UI для просмотра запусков, логи, ручной перезапуск, настройку расписания без редактирования crontab. Для DE это стандарт.

**Почему SCD Type 2, а не просто UPDATE?** Потому что история важна. Хочется знать: «а какая цена была на этот рейс неделю назад?» — с обычным UPDATE этого не узнать.

**Почему не Kafka + Debezium + Flink?** Изначально задумывался именно такой стек (как практика CDC). Но для одного источника данных и небольшого объёма это был бы избыточный overhead. Python + PostgreSQL — правильное решение, не компромисс.

## Что видно снаружи

- **Grafana на `localhost:3000`** — графики и история цен
- **Prefect на `localhost:4200`** — управление расписанием и запусками
- **Telegram** — уведомления при падении цены

Всё поднимается одной командой: `docker compose up`
