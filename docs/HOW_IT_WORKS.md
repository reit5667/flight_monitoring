# Как работает Flight Monitor — простым языком

## Суть проекта

Есть конкретная задача: найти наиболее выгодный способ добраться из точки A в точку B — не обязательно прямым рейсом, не обязательно с одним пересадочным городом. Авиаагрегаторы показывают цены в моменте, но не отвечают на вопрос "а когда лучше купить?" и не следят за изменениями.

Эта система делает именно это: задаёшь маршруты, которые тебя интересуют, система регулярно собирает цены со всех источников, отслеживает динамику и присылает уведомление в Telegram когда появляется выгодное предложение.

При этом система устроена как настоящая Data Platform — с историей изменений, аналитикой и всеми лучшими практиками Data Engineering.

---

## Из чего состоит система

Представь конвейер: данные входят с одного конца, обрабатываются по шагам, и на выходе ты получаешь уведомление или график.

### Шаг 1 — Планировщик (Prefect)

Каждые N минут (настраивается) автоматически запускается задача. Она спрашивает базу данных: "какие маршруты нужно проверить прямо сейчас?" Маршруты с высоким приоритетом проверяются чаще.

Prefect — это как cron, только с UI, логами и возможностью запустить задачу вручную одной кнопкой.

### Шаг 2 — Коннекторы (Aviasales, Trip.com, Agoda)

Для каждого маршрута система идёт на сайты и получает актуальные цены. Важный момент: **мы не парсим HTML** (это ненадёжно, сайты меняют вёрстку). Вместо этого мы используем Playwright, чтобы открыть браузер, дождаться пока сайт загрузит данные, и перехватить XHR-запрос — тот самый JSON, который сайт получает от своего собственного сервера.

Это надёжнее: структура JSON меняется реже, чем HTML.

Каждый коннектор — отдельный файл, все они работают по одному интерфейсу (BaseConnector). Хочешь добавить Booking.com — создаёшь ещё один файл, не трогая остальные.

### Шаг 3 — Raw Storage

**Сразу после получения** JSON сохраняется как файл на диск (raw_storage/aviasales/1/2024-01-15T10:00:00.json). Зачем? Если завтра выяснится, что парсер работал с багом — можно перепарсить старые данные без повторного запроса к сайту. Это важный принцип: сырые данные неизменны.

В базу данных записывается только метаинформация: где лежит файл, сколько рейсов, когда сохранено.

### Шаг 4 — Парсеры

Сырой JSON у каждого сайта свой, разный. Парсер превращает его в единую модель `Flight` — набор полей, одинаковый для всех источников:

```
Aviasales JSON → parser/aviasales.py → Flight(provider="aviasales", price=120, ...)
Trip.com JSON  → parser/trip.py      → Flight(provider="trip", price=115, ...)
```

После парсера данные уже сравнимы между собой.

### Шаг 5 — CDC Engine (сердце системы)

CDC расшифровывается как Change Data Capture — захват изменений данных.

Обычно CDC — это когда база данных сама отдаёт поток изменений. Но у нас внешние сайты, они ничего не отдают. Поэтому мы строим CDC сами: сравниваем два последовательных списка рейсов и находим разницу.

```
10:00 → [AirAsia: 120 USD, Malaysia Airlines: 150 USD]
11:00 → [AirAsia: 105 USD, Batik Air: 90 USD]

CDC находит:
  UPDATE: AirAsia: 120 → 105  (цена упала)
  INSERT: Batik Air: 90        (новый рейс появился)
  DELETE: Malaysia Airlines    (рейс исчез)
```

**CDC Engine — это чистая функция**: принимает два списка, возвращает список событий. Не обращается к базе данных. Это важно для тестируемости — можно проверить логику без поднятия PostgreSQL.

### Шаг 6 — Warehouse (PostgreSQL)

События от CDC применяются к трём таблицам:

**flights_current** — актуальное состояние прямо сейчас. Как фотография: одна запись на рейс, всегда обновлённая.

**flights_history** — полная история. Никогда ничего не удаляется. Если цена изменилась 5 раз — в таблице 5 записей, у каждой есть дата начала действия и дата окончания. Это называется SCD Type 2 (Slowly Changing Dimension) — стандартный паттерн в Data Engineering.

```
valid_from       valid_to         price   is_current
2024-01-15 10:00  2024-01-15 11:00  120     false
2024-01-15 11:00  null              105     true
```

**cdc_events** — лог всех событий с подробностями: что изменилось, было и стало.

### Шаг 7 — Уведомления

После применения CDC проверяются правила:
- Цена стала ниже твоего порога (max_price в настройках маршрута)?
- Цена упала больше чем на 10%?
- Это новый исторический минимум?

Если да — в Telegram приходит сообщение с деталями рейса.

Есть дедупликация: если цена держится на минимуме 3 часа — уведомление не будет приходить каждый час, только один раз.

### Шаг 8 — Grafana

Grafana подключена напрямую к PostgreSQL и строит графики по SQL-запросам. Никакого дополнительного API не нужно.

Дашборды:
- История цены по маршруту (из flights_history)
- Минимум и среднее за период
- Лучшие текущие предложения (из flights_current)
- Активность CDC за сутки (сколько INSERT/UPDATE/DELETE)

## Почему именно такая архитектура

**Почему Raw Storage?** Структура XHR API сайтов меняется. Если мы сохраняем сырые данные, то при смене формата нужно только поправить парсер и перепрогнать старые файлы — данные не теряются.

**Почему отдельная таблица маппингов (source_route_mappings)?** Aviasales использует код "MOW" для Москвы, Trip.com — "SVO". Маршрут один и тот же, но коды разные. Таблица маппингов решает это без дублирования маршрутов.

**Почему Prefect, а не cron?** Prefect даёт UI для просмотра запусков, логи, ручной перезапуск, настройку расписания без редактирования crontab. Для Data Engineering это стандарт.

**Почему SCD Type 2, а не просто UPDATE?** Потому что история важна. Хочется знать: "а какая цена была на этот рейс неделю назад?" — с обычным UPDATE этого не узнать.

## Маршруты в базе данных

Маршруты — это конфигурация. Ты добавляешь запись в таблицу `routes`:

```
origin: HAN  (Ханой)
destination: KUL  (Куала-Лумпур)
date_from: 2024-09-01
date_to: 2024-09-30
max_price: 200  (уведомить если дешевле 200 USD)
priority: 100
search_interval: 60  (проверять раз в час)
enabled: true
```

И для каждого источника — маппинг как его запрашивать:

```
source: aviasales,  source_origin: HAN, source_destination: KUL
source: trip,       source_origin: HAN, source_destination: KUL
source: agoda,      source_origin: HAN, source_destination: KUL
```

## Что видно снаружи

- **Grafana на localhost:3000** — графики и история цен
- **Prefect на localhost:4200** — управление расписанием и запусками
- **Telegram** — уведомления при падении цены

Всё поднимается одной командой: `docker compose up`

## Слои данных (Data Layers)

В Data Engineering принято разделять данные на слои:

| Слой | Что это | Где лежит |
|---|---|---|
| **Raw** | Исходный JSON с сайта, без изменений | raw_storage/ (файлы на диске) |
| **Silver** | Нормализованные Flight объекты | Память (Python объекты) |
| **Gold** | Агрегаты: мин цена, история, лучшие предложения | PostgreSQL views / Grafana |

Bronze-слой в нашем случае пропущен: парсер сразу даёт нам Silver, не нужен промежуточный слой.
